# Lago OpenAPI

OpenAPI 3.1 description of the Lago API. The [lago-api](https://github.com/getlago/lago-api) code is the source of truth: when the spec and the code disagree, the code decides.

## Layout and commands

- `src/openapi.yaml` is the root document: it lists the `tags`, `paths` and `webhooks`. Paths live in `src/resources/`, schemas in `src/schemas/`, and shared pieces in `src/parameters/`, `src/responses/` and `src/webhooks/`.
- The root `openapi.yaml` is generated by `npm run build`. Never edit it by hand. Run the build after every change under `src/` and commit the regenerated file with it. CI fails when the committed bundle differs from a fresh build.
- `npm run test` builds, then runs `redocly lint` and `spectral lint`. It must pass before a commit.
- This repository is public. Never put real API keys, customer data or internal links in the spec, commits or PRs.

## Checking a change against lago-api

- Paths: `config/routes.rb`.
- Request fields and query filters: the controller's `params.permit` and the services it calls.
- Response fields: the serializer in `app/serializers/v1/`.
- Types, enums and nullability: the model (validations, enums) and `db/structure.sql`.
- Webhooks: `config/webhook_event_types.yml` and `app/services/webhooks/`.

## Naming

- Resource files are snake_case: `<plural>.yaml` for the collection path, `<singular>.yaml` for one record, `<singular>_<action>.yaml` for an action path. Every file under `src/` uses the `.yaml` extension, never `.yml`. Each path is registered under `paths` in `src/openapi.yaml`.
- Schemas are PascalCase and follow these suffixes:
  - `<Name>Object`: the resource as lago-api returns it.
  - `<Name>`: the response wrapper, `{ <singular>: <Name>Object }`.
  - `<Plural>Paginated`: the list response, `{ <plural>: [<Name>Object], meta: PaginationMeta }`.
  - `<Name>CreateInput` and `<Name>UpdateInput`: request bodies wrapped in the root key lago-api expects, usually built on a shared `<Name>BaseInput`.
  - `<Name>Enum`: an enum used by several schemas.
- Reuse the parameters in `src/parameters/` (`page`, `per_page`, `external_customer_id`, ...) before adding a new one.

## Operations

- `summary` is a short label without a period: `List all add-ons`, `Retrieve an add-on`, `Create an add-on`, `Update an add-on`, `Delete an add-on`.
- `operationId` is camelCase: `findAll<Plural>`, `find<Name>`, `create<Name>`, `update<Name>`. For other actions, follow the names already used by the same resource.
- Each operation has one tag, declared under `tags` in `src/openapi.yaml`.
- Success is `200`, also for creation: lago-api does not return `201`.
- List only the error statuses the controller can return, as `$ref` to `src/responses/`. Every operation has `401`. The others map to lago-api failures:
  - `400`: a root key read with `params.require` is missing (`ActionController::ParameterMissing`).
  - `403`: `forbidden_failure!` (premium feature, API key permissions).
  - `404`: `not_found_failure!`.
  - `405`: `not_allowed_failure!` (the action is not allowed in the record's current state).
  - `422`: `validation_failure!` or `single_validation_failure!`.
- A `requestBody` that lago-api reads a root key from has `required: true`.

## Descriptions

- Property, parameter and operation descriptions are full sentences that end with a period, including multi-line descriptions and descriptions that end with a code span.
- Tag, request body, response and webhook descriptions are short labels without a period (`Payment request created`).
- Descriptions are for API users, who may not use Ruby. They never name lago-api internals: Ruby or Rails types (`BigDecimal`, `nil`, `Hash`), class, serializer or service names, or database tables. Write `null`, "object" or "decimal string" instead.
- A deprecated property or parameter has `deprecated: true` and a description that starts with `**Deprecated.**` (enforced by `.spectral.yml`).

## Types, formats and examples

- Lago identifiers use `format: uuid`, timestamps `format: date-time` and dates `format: date`.
- Every scalar property has an `example`. Examples use fake data: the UUID `1a901a90-1a90-1a90-1a90-1a901a901a90`, `.example` email domains (`dinesh@piedpiper.example`), which RFC 2606 reserves for documentation, UTC timestamps such as `"2022-04-29T08:59:51Z"`.
- Enum values match the lago-api constant or model enum exactly. Never document internal Ruby class names as enum values or examples.

## Decimal values sent as strings

lago-api sends decimal columns (units, rates, precise amounts, conversion rates, alert values) as JSON strings. Every such value is documented as a string with a `pattern` and a string example, including a value changed from `type: number` to `type: string`:

```yaml
type: string
pattern: "^[0-9]+(\\.[0-9]+)?$"
description: Number of units consumed, sent as a decimal string.
example: "12.5"
```

- Use the pattern above only when the value cannot be negative: lago-api validates it as 0 or more, or computes it from values that cannot be negative. Otherwise, including when lago-api does not check the sign, use `"^-?[0-9]+(\\.[0-9]+)?$"`.
- The same applies when the value is nullable (`type: [string, "null"]`).
- Older schemas use `"^[0-9]+.?[0-9]*$"`, where the unescaped `.` matches any character. Do not copy it.
- The description says "sent as a decimal string" (or "a number or a decimal string" for an input that accepts both). Never write `BigDecimal` or other Ruby terms in the spec: some existing descriptions say "formatted as a BigDecimal", and that wording is not copied.
- Amounts in cents (`*_amount_cents`) are integers, not decimal strings.

## Nullability

- A nullable value is written `type: [<type>, "null"]` (OpenAPI 3.1). Do not use `nullable: true`.
- A response value is nullable when its column has no `NOT NULL` in `db/structure.sql`, or when the serializer can return `nil` for it.

## Required fields

Check the `required` list every time a property is added, removed or made nullable, in the same change.

- Response schemas: `required` lists every key the serializer always sends, including keys whose value can be `null`. A key sent only in some cases (an `includes` option, a feature flag, a condition in the serializer) is not required.
- Request schemas: `required` lists only the fields lago-api rejects when they are missing (`params.require`, a presence validation, or a validation error from the service). A field with a default, or one needed only for some types, is optional and its description says when it is needed.
- Every name in `required` exists under `properties`.
- Removing a key from a response `required` list, or adding a field to a request `required` list, is a breaking change. Call it out in the PR description.

## Webhooks

- One file per event in `src/webhooks/<object>_<action>.yaml`, registered under `webhooks` in `src/openapi.yaml`.
- Each one is a `post` with the `webhook_signature`, `webhook_signature_algorithm` and `webhook_unique_key` parameters, a body with `webhook_type`, `object_type`, `organization_id` and the object (a `$ref` to its `<Name>Object`), and a `200` response.
- `webhook_type` matches the event name in `config/webhook_event_types.yml`.
